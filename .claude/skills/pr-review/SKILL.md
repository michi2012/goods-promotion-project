# /pr-review — 팀원 방식 PR 리뷰 (범용)

현업처럼 **PR을 올린 뒤** 팀원이 리뷰하고, 작성자가 반영한다. 테스트·E2E는 지금처럼 커밋 전에 하고, 리뷰만 PR 뒤에 한다.
프로젝트별 값(위험 변경 기준, 제외 파일, 맥락 문서, 전용 점검)은 **같은 폴더의 `project.md`**.

사용법: `/pr-review` (현재 브랜치의 PR) · `/pr-review {PR번호}` · `/pr-review {PR번호} --since {커밋}` (재리뷰)

## 흐름

```
1. 대상 수집      PR 정보·diff를 파일로 저장 (메인 컨텍스트에 diff를 싣지 않는다)
2. 리뷰어 호출    code-reviewer 서브에이전트 — 작성자 설명 없이
3. 미리보기       사용자에게 코멘트 전체를 보여주고 빼거나 고칠 것을 받는다
4. 게시          승인 후 PR review 1개로 게시 (줄 단위 + 요약)
5. 반영          [필수]는 반영 커밋, 나머지는 답글로 판단 기록
6. 재리뷰        반영 커밋만 --since로 다시 본다
```

### 1. 대상 수집
- `gh pr view {n} --json number,title,url,headRefOid,baseRefName,files` 로 PR 정보를 얻는다.
- `gh pr diff {n} > {스크래치패드}/pr-{n}.diff` 로 diff를 **파일에 저장**한다. 재리뷰면 `git diff {since}..{headRefOid}` 를 저장한다.
- 변경 파일에서 `project.md`의 **제외 파일**을 뺀다. 남은 파일이 없으면 "리뷰할 코드 변경 없음"으로 끝낸다.
- 관련 명세 경로를 찾는다 (`project.md` "맥락 문서").

### 2. 리뷰어 호출
`code-reviewer` 에이전트를 부른다. 프롬프트에는 **아래만** 넣는다.
- PR 번호·제목·URL, head 커밋, diff 파일 경로, 리뷰할 파일 목록
- 관련 명세 경로, `project.md` 경로
- **게시용 JSON 출력 경로** `{스크래치패드}/pr-{n}-review.json` — 리뷰어가 이 파일에 게시할 본문을 직접 쓴다
- 재리뷰면: 이전 리뷰의 [필수] 목록과 "이 커밋들에서 반영됐는지 확인"

**넣지 않는 것**: 작성자(구현 세션)의 의도·설계 설명·"이 부분은 괜찮다" 같은 판단, PR 본문의 영향도·테스트 서술. 리뷰어가 작성자 판단에 끌려가지 않게 하려는 것이 새 컨텍스트로 띄우는 이유다.

에이전트가 실패하거나 응답이 없으면 → 사용자에게 알리고 대체 수단(내장 `/code-review`)을 제안한다. 대신 작성 세션이 직접 리뷰하지 않는다.

### 3. 미리보기 (게시 전 필수)
리뷰어가 쓴 JSON 파일을 기준으로 보여준다 (게시될 내용과 미리보기가 같아야 한다).
- 요약표: 판정, [필수]/[제안]/[질문]/[사소] 건수
- 코멘트 전문 (위치·본문). JSON 파일 경로도 함께 알려 사용자가 원문을 직접 열어볼 수 있게 한다
- 작성 세션의 의견은 **분리해서** 덧붙일 수 있다 ("이 지적은 오탐으로 보임 — 근거"). 리뷰어 본문을 고쳐 쓰지 않는다.

사용자가 뺄 코멘트를 정하면 JSON에서 **그 항목만 지운다**. 문구를 바꾸고 싶으면 사용자 승인 후 리뷰어에게 다시 쓰게 한다. **명시적으로 승인하면** 게시한다. 승인 없이는 게시하지 않는다 (공개 PR에 남는다).

### 4. 게시
PR review 하나로 줄 단위 코멘트와 요약을 함께 올린다.
- **리뷰어가 쓴 JSON 파일을 그대로** `gh api repos/{owner}/{repo}/pulls/{n}/reviews --method POST --input {파일}`. 작성 세션은 본문을 다시 타이핑하거나 줄이지 않는다 (옮겨 적다 보면 작성자 판단이 섞이고 토큰도 든다)
  ```json
  { "commit_id": "{headRefOid}", "event": "COMMENT", "body": "{요약 코멘트}",
    "comments": [ { "path": "{파일}", "line": {head 기준 줄}, "side": "RIGHT", "body": "{코멘트}" } ] }
  ```
- `event`는 항상 `COMMENT`. 같은 계정의 PR이라 APPROVE·REQUEST_CHANGES는 쓸 수 없다. 판정은 요약 본문에 쓴다.
- 줄 단위는 [필수]·[제안]·[질문]만, **diff 안의 줄**만. [사소]와 diff 밖 지적은 요약에 모은다.
- API가 줄 번호로 거절하면(422) 해당 코멘트를 요약으로 옮겨 다시 게시한다.
- 게시 후 review URL을 보고한다.

### 5. 반영 (작성자)
반영 요청("PR #n 리뷰 코멘트 반영해줘", "C1만 반영", "답글 확인해줘")을 받으면, 리뷰한 세션이 아니어도 되도록 **GitHub에서 먼저 읽는다**:
- 줄 단위 코멘트·답글: `gh api repos/{owner}/{repo}/pulls/{n}/comments` (`id`, `path`, `line`, `body`, `in_reply_to_id`, `user.login`)
- 요약 코멘트: `gh api repos/{owner}/{repo}/pulls/{n}/reviews`
- 표시([필수]/[제안]/[질문])별로 묶고, 이미 답글이 달린 것과 사용자가 GitHub에서 직접 단 답글(반론·결정)을 구분해 보여준 뒤 처리 계획을 확인받는다.

| 표시 | 머지를 막나 | 작성자가 할 일 |
|---|---|---|
| [필수] | 막음 | 고친다 → "리뷰 반영" 커밋 → 코멘트에 커밋 해시로 답글 |
| [제안] | 안 막음 | 반영하거나, 안 하는 이유를 답글. 나중에 할 일이면 백로그 ID를 답글에 |
| [질문] | 안 막음 | 답글로 설명. 코드로만 알 수 없는 결정이면 주석·설계 노트 보강 |
| [사소] | 안 막음 | 무시해도 된다 |

- 답글: `gh api repos/{owner}/{repo}/pulls/{n}/comments/{comment_id}/replies --method POST -f body=...` (게시 전 사용자 확인)
- [필수]를 고칠 때도 CLAUDE.md의 PR 범위 원칙·테스트 동반 원칙을 따른다.
- 이미 머지된 PR이면 반영은 새 브랜치에서 한다 (백로그로 등록 후). 원래 코멘트에는 새 PR 링크로 답글.

### 6. 재리뷰
`/pr-review {n} --since {리뷰 당시 head}` — 반영 커밋의 diff만 보고, 이전 [필수]가 해결됐는지와 새로 생긴 문제만 확인한다. 전체를 다시 리뷰하지 않는다. 결과는 같은 방식(미리보기 → 승인 → 게시)으로 남긴다.

## 코멘트 형식

줄 단위 코멘트:
```
**[필수]** {무엇이 문제인가 — 구체적 상황}
{어떤 입력/상태에서 어떤 잘못된 결과가 나는가}
**제안:** {고치는 방향}
근거: {명세 P-n/S-n·규칙·설계 노트 등}
```
요약 코멘트:
```
## 리뷰 요약
**판정: 머지 가능 / 수정 필요** — {한 줄}
| 구분 | 건수 |  ([필수] / [제안] / [질문])
**[사소] (답글 불필요)** - ...
**확인한 것:** {명세 시나리오·점검 항목 중 실제로 확인한 것}
**좋았던 점:** {진짜 잘된 것만 1~2개}
```
- 판정: [필수]가 0건이면 "머지 가능", 있으면 "수정 필요".

## 규칙
1. **[필수]는 리뷰어가 재검증한 것만.** 리뷰어가 지적한 줄과 관련 코드를 다시 읽어 실제로 성립하는지 확인한 것만 [필수]로 남긴다. 확신이 없으면 [질문]으로 내린다.
2. **PR당 1회.** 위험 변경(`project.md`)이면 필수, 아니면 선택. 단계마다 돌리지 않는다.
3. **토큰 절약.** diff 중심으로 읽고, 주변 코드는 판단이 안 될 때만 필요한 부분만. 큰 문서는 키워드로 발췌. 재리뷰는 반영 diff만.
4. **리뷰어는 코드를 고치지 않는다.** 고치는 것은 작성자(반영 단계)다.
5. **게시·답글은 사용자 승인 후.** 외부(공개 저장소)에 남는다.
6. **결과 기록.** 리뷰 결과(판정, [필수] 건수, review URL)를 `docs/checklist.md` 최종 검증에 적는다.
