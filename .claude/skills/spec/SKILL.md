# /spec — 요구사항 → 설계 → 문서화 (범용)

요구사항을 입력받아 질문으로 자세히 다듬고, 문서 하나로 확정한 뒤 구현(`/plan`)으로 넘긴다.
프로젝트별 값(문서 위치, 계약 파일, 백로그·이슈 트래커)은 **같은 폴더의 `project.md`**, 문서 양식은 `template.md`.

## 언제 쓰나

| 작업 | 진행 |
|------|------|
| 문서만 수정, 또는 파일 1개 단순 수정 | 바로 진행 |
| 코드 파일 2개 이상, 정책 없음 (인프라·리팩터링·버그 수정·성능 개선) | `/plan` → 구현 |
| 정책·계약이 있는 기능 (누가·언제·얼마·예외 시 어떻게, 새 API·이벤트·테이블) | **`/spec`** → `/plan` → 구현 |

애매하면 사용자에게 묻는다.

## 흐름

```
[/spec]
 1. 질문          빠진 정책·예외·범위를 묻는다
 2. 요구사항 확인  문서의 요구사항 부분 작성 → 사용자 확인 → "요구사항 확인 ☑"
 3. 설계 확인      문서의 설계 부분 작성 → 사용자 확인 → "설계 확인 ☑" → 작업 등록
[구현 — 기존 방식]
 4. /plan         문서를 확정된 전제로 읽고 구현 계획만 세운다
 5. 구현           코드 + 테스트 (+ 계약 파일 수정)
 6. PR            문서 + 코드를 함께 머지
```

- 이미 문서가 있으면 맨 위 확인 표시를 보고 이어서 진행한다.
- 서로 영향을 주는(상태·데이터를 공유하는) 기능은 **한 문서**에 기능별 섹션으로 쓴다. 1~3은 한 번, 4~6은 기능마다 반복한다.

## 규칙

1. **결정은 사용자가 한다.** Claude는 질문하고 선택지·추천을 낸다. 문서에 결정을 임의로 채우지 않는다.
2. **질문은 중요한 것부터 몇 개씩**, 각 질문에 선택지와 추천을 붙인다. 사용자·CS, 금액·정산, 법·약관, 운영, 동시성(같은 요청 두 번) 관점에서 빠진 것을 찾는다.
3. **법·약관 근거는 단정하지 않는다.** 결정 기록에 "확인 필요"로 두고, 사용자가 출처를 확인한 뒤 확정한다.
4. **요구사항이 확인된 뒤 설계한다.** 설계 중 요구사항 구멍이 보이면 요구사항으로 돌아가 고친다.
5. **설계는 바꾸기 비싼 것만 정한다**: DB 변경, API, 이벤트, 장애 시 동작, 새 기술. 클래스 구조·쿼리 세부·인덱스 튜닝은 구현 때 정한다.
6. **확인 후 변경은 변경 이력에 남긴다.** 덮어쓰지 않는다.
7. **문서는 첫 구현 PR에 같이 넣는다.** 구현을 한참 미룰 때만 문서를 먼저 커밋한다.
8. 3단계까지 코드·마이그레이션을 만들지 않는다.
9. 사용자에게 확인을 요청할 때는 **"지금 결정 필요"**(답해야 다음 단계로 감)와 **"기록만"**(문서에 "확인 필요"로 남기고 진행)을 나눠서 쓴다. "지금 결정 필요"에는 추천안을 붙인다.
