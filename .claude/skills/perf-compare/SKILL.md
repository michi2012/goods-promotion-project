# 성능 전후 비교 원칙 (범용)

세 가지를 지킨다.
1. **한 번에 하나만 바꾼다.** 두 가지를 같이 바꾸면 어느 쪽 효과인지 말할 수 없다.
2. **같은 조건에서 반복 측정한다.** 한 번 잰 숫자는 근거가 아니다.
3. **최종 처리까지 잰다.** 비동기 응답(202 등)은 "접수"일 뿐이다. 응답 TPS와 실제 처리 완료 속도를 따로 본다.

이 프로젝트에 적용하는 값(환경, 시나리오 위치, 지표 수집 위치)은 같은 폴더의 `project.md`.

## 1. 절차

| 단계 | 할 일 |
|------|------|
| ① 가설 | "X를 바꾸면 지표 Y가 Z만큼 좋아진다"를 먼저 적는다. 무엇을 볼지 측정 전에 정한다 |
| ② 스모크 | 1 VU·짧은 시간으로 스크립트와 대상이 정상인지 확인 (에러율 0, 기대 응답). 본 측정 아님 |
| ③ 기준선 | 변경 전 상태로 본 측정. 워밍업 후 **3회 이상** 반복 |
| ④ 변경 | 가설의 변수 하나만 바꾼다 |
| ⑤ 재측정 | ③과 같은 스크립트·데이터·환경으로 같은 횟수 |
| ⑥ 판단 | 반복 간 편차보다 작은 차이는 "차이 없음". 좋아졌어도 보조 지표로 원인을 설명할 수 있어야 한다 |
| ⑦ 기록 | 2. 기록 형식대로 남긴다. 나빠졌거나 차이 없음도 기록한다 |

- 기준선은 가능하면 **같은 날 다시 잰다.** 며칠 전 숫자와 비교하면 환경 차이가 섞인다.
- 결과 수치는 반복의 **중앙값**을 쓰고, 최소·최대도 함께 적는다.

## 2. 조건 고정 (전후가 같아야 하는 것)
- 데이터 양·분포 (시드 스크립트로 재현 가능하게). 인덱스·쿼리 비교는 데이터가 충분히 커야 차이가 보인다
- 캐시 상태: 콜드/웜 중 무엇으로 쟀는지 명시. 비교하는 두 쪽은 같은 상태로
- 부하 모양: VU 수, 시간, 시나리오(executor), think time
- 환경: 같은 머신·인스턴스 타입, 다른 부하 없음, 같은 설정(풀 크기, JVM 옵션)
- 부하 발생기: 대상과 다른 머신에서 돌리는 게 원칙. 같은 머신이면 그 사실을 기록한다 (k6 자체가 CPU를 먹는다)

## 3. 무엇을 잴까 — 공통 지표 + 기술별 보조 지표

공통 (k6): 처리량(RPS/TPS), 지연 p95·p99, 에러율. 평균은 참고만.

| 바꾼 것 | 보조 지표 (원인 설명용) |
|------|------|
| 인덱스·쿼리 | `EXPLAIN`/`EXPLAIN ANALYZE`의 type·rows·실행 시간, 슬로 쿼리 수 |
| 캐시(Redis 등) | 캐시 hit율, DB 쿼리 수 감소, 캐시 미스 시 지연 |
| 메시지 큐(Kafka 등) | consumer lag, 발행→처리 완료 시간, 최종 처리 완료까지 걸린 시간 |
| 배치 | 총 소요 시간, 초당 처리 건수, 스텝별 시간 (배치 메타 테이블) |
| 스레드·커넥션 풀 | 활성 스레드·커넥션 수, 대기 시간, 풀 포화 여부 |
| 인프라 증설 | CPU·메모리 사용률 — 자원이 병목이었는지 |

- 지연이 줄었는데 보조 지표가 그대로면 측정 노이즈나 다른 원인을 의심한다.
- 처리량이 올랐는데 다른 곳(DB, 다운스트림)이 밀리면 개선이 아니라 병목 이동이다.

## 4. 환경별 해석

| 환경 | 의미 있는 것 | 주의 |
|------|------|------|
| 로컬 (docker compose) | 같은 조건에서 하나만 바꾼 **상대 비교** | 절대 수치는 운영 근거로 쓰지 않는다. 컨테이너들이 자원을 공유한다 |
| 클라우드 (EC2·EKS 등) | 상대 비교 + 절대 수치 (스펙 명시 시) | 부하 발생기는 별도 인스턴스. 인스턴스 타입·리전 기록. 비용 생기므로 측정 후 정리 |

## 5. 기록 형식
결과 파일 하나에 다음을 담는다. 위치는 `project.md`.

```markdown
# {주제} 전후 비교 — YYYY-MM-DD

- 가설: ...
- 바꾼 것 (하나): ...
- 환경: 머신/인스턴스, 데이터 N건, 캐시 콜드/웜, 부하 발생기 위치
- 부하: 스크립트 경로, VU, 시간, executor
- 반복: N회 (워밍업 M초)

| 지표 | 전 (중앙값, 최소~최대) | 후 | 변화 |
|------|------|------|------|
| TPS | | | |
| p95 | | | |
| 에러율 | | | |
| {보조 지표} | | | |

- 판단: 개선 / 차이 없음 / 악화 — 근거 (보조 지표로 원인 설명)
- 원자료: k6 summary JSON 경로, 대시보드 캡처
```

- k6는 `--summary-export <파일>.json`으로 원자료를 남긴다.

## 6. 자가 점검
- [ ] 가설과 볼 지표를 측정 전에 적었는가?
- [ ] 바꾼 변수가 하나인가?
- [ ] 전후 조건(데이터·캐시·부하·환경)이 같은가?
- [ ] 3회 이상 반복했고, 차이가 반복 간 편차보다 큰가?
- [ ] 비동기 처리라면 최종 처리 완료까지 쟀는가?
- [ ] 보조 지표로 개선 원인을 설명할 수 있는가?
- [ ] 결과(악화·차이 없음 포함)를 기록 형식대로 남겼는가?
