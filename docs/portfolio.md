## 문제 해결·설계 결정

작업이 끝났을 때(PR 머지 후) 아래 **4개 질문이 모두 "예"**면 추가한다. 기능을 만든 것 자체가 아니라 **해결한 문제**를 적는다.

| 질문 | 거르는 것 |
|---|---|
| 1. **해결한 문제가 있었나?** 무엇이 잘못됐거나 위험했는지 영향(돈·데이터 정합성·장애·성능)을 한 문장으로 쓸 수 있다 | 단순 기능 구현 ("환불 API를 만들었다") |
| 2. **원인을 파고들었나?** 문제가 생기는 조건이나 근본 원인을 설명할 수 있다 | 원인이 뻔한 수정 (오타·설정 누락) |
| 3. **대안을 비교해서 골랐나?** | 정답이 하나뿐이던 수정 |
| 4. **해결을 증명할 수 있나?** 테스트·E2E·수치로 전후를 보여줄 수 있다 | 말로만 설명 가능한 것 |

- 같은 문제를 여러 PR로 풀었으면 **한 사례로 묶어** 마지막 PR 머지 후 적는다 (면접에서 몇 분 설명할 크기). 목록에 한 줄 + "사례"에 템플릿 형식.
- 리뷰 지적 반영·알람 조정처럼 그 문제의 일부를 고친 것은 따로 적지 않는다. 그 이야기를 풀 때 세부로 꺼낸다.
- 개발 프로세스·도구 개선(리뷰 skill 등)은 시스템 문제가 아니므로 이 표에 적지 않는다.

## 사례

### 작성 형식

```
### **[기술] 결과가 보이는 제목 — 핵심 결정**

- **🚨 문제 : 한 줄 요약**
    - 상황과 영향(돈·정합성·장애·성능). 무엇이 필요했고 왜 기존 방식으로는 부족했는지
- **⚖️ 대안 비교 및 기술 선정 :**
    - **선정 축 (대안 A vs <u>채택</u>) :** 검토한 이유와 고른 이유
    - **[대안 - 배제] / [방식 - 도입] :** 핵심 결정만. 남는 한계와 보완 계획은 하위 항목으로
- **🛠️ 조치 : 한 줄 요약**
    - 적용한 구조. 이유가 강한 것만
- **📈 성과 : 한 줄 요약**
    - 테스트·E2E·수치로 본 전후
- **🔁 회고 : (필요할 때만)**
    - 다시 한다면 바꿀 것, 예상과 달랐던 것
```

**쓰는 기준 — 면접관이 30초 안에 "무슨 문제, 왜 이 기술, 뭐가 좋아졌나"를 읽을 수 있게**
- **핵심 결정은 2~3개.** 섹션당 항목 2~3개, 분량은 한 화면 안. 나머지 결정(세부 설정·리뷰 반영·알람 기준 등)은 넣지 않고 면접 예비 답변으로 둔다 — 원본(명세·PR)에 있다.
- **대안은 실제로 검토한 것만.** 검토하지 않은 기술을 비교 대상으로 쓰지 않는다 ("왜 버렸나"에 답할 수 없다).
- **문제는 반박당하지 않게.** "기존 도구가 나쁘다"가 아니라 "이 요건이 필요했고, 기존 방식으로는 직접 만들어야 했다"로 쓴다.
- **사실 그대로.** 모의·로컬 환경이면 밝힌다. 규모 수치가 아직 없으면 성과에 "측정 예정"으로 남기고 측정 후 채운다.
- **내부 용어 금지.** 백로그 ID(BL-xxx)·클래스명·설정 키 대신 풀어 쓴다.

<a id="pg-reconciliation"></a>
### **[Spring Batch] 재실행해도 같은 결과, 실패해도 이어서 — 하루치 PG 대사 배치**

- **🚨 문제 : 하루치 결제 대사에 필요한 '부분 커밋·재시작·결정적 결과'**
    - 실시간 보정이 놓친 돈 흐름의 어긋남을 잡기 위해, 하루치 결제 기록을 PG사 일자별 거래 파일과 비교하는 **사후 대사**가 필요했습니다. (실제 PG 대신 모의 PG가 실제 대사 파일 방식대로 일자별 CSV를 만듭니다.)
    - 대량을 한 번에 처리하는 작업이라 기존 주기 작업(소량을 짧게 처리하는 `@Scheduled`)과 요건이 달랐습니다. 단순하게 구현하면 감시선 자체가 틀립니다.
        - 한 트랜잭션으로 처리하면 **중간 실패 시 처리분 전체가 롤백**됩니다.
        - 상태 조건 + OFFSET으로 읽으면 **처리 도중 바뀐 건이 누락**됩니다.
        - 현재 상태로 비교하면 **실행 시점마다 결과가 달라져** 같은 날짜를 다시 돌려도 믿을 수 없습니다.

- **⚖️ 대안 비교 및 기술 선정 :**
    - **실행 방식 (스케줄러 + 직접 구현 vs <u>Spring Batch</u>) :** 의존성 없이 스케줄러와 진행 위치 테이블로 직접 만드는 방안을 검토했습니다. 하지만 chunk 커밋, 진행 위치 저장, 실패 지점부터 재시작, 같은 날짜 중복 실행 방지를 **모두 직접 구현**해야 하고, 그 코드가 곧 버그의 원천입니다. 이를 표준으로 제공하는 Spring Batch를 채택했습니다.
    - **[현재 상태 비교 - 배제] / [이벤트 시각 기준 비교 - 도입] :** 승인·취소 시각을 기록하고, 대사일 하루 범위 안의 **이벤트만** 비교합니다. 다음 날 일어난 취소는 다음 날 대사 대상이 되므로 **언제 실행해도 결과가 같습니다.**
    - **[OFFSET 페이징 - 배제] / [키셋 페이징 - 도입] :** (이벤트 시각, id) 기준으로 읽어 처리 중 상태가 바뀌어도 대상이 흔들리지 않고, 마지막으로 읽은 키가 **그대로 재시작 위치**가 됩니다.
        - **남은 한계 :** 거래 파일을 서버 로컬에 두어 단일 인스턴스를 전제합니다. 다중 인스턴스는 공유 저장소 도입 후 보완할 예정입니다.

- **🛠️ 조치 : 끊기지 않는 운영 흐름**
    - 매일 새벽 자동 실행 + 관리자 수동 실행. 같은 날짜의 마지막 실행이 **실패면 실패 지점부터 재시작**, 성공이면 결과를 새로 계산해 교체합니다.
    - 서버가 대사 도중 내려가면 실행이 '진행 중'으로 남아 재시작이 막히는 문제를, **기동 시 실패 처리**로 풀었습니다 (Spring Batch가 자동으로 해주지 않는 부분).
    - 불일치는 자동 보정하지 않고(잘못 보정하면 돈이 움직임) **기록 + 알람**으로 사람에게 넘깁니다.

- **📈 성과 : 단순 구현에서 깨지는 조건을 재현하고, 설계로 통과**
    - **재시작 :** 한 트랜잭션은 전체 롤백 / Batch는 커밋분을 유지하고 **남은 건만 읽어** 한 번에 성공한 것과 같은 결과
    - **누락 :** OFFSET은 처리 중 취소로 **2건 누락** / 키셋은 **전부 판정**
    - **결정적 결과 :** 현재 상태 비교는 다음 날 취소 전후로 결과가 바뀜 / 이벤트 시각 비교는 재실행해도 동일
    - **실제 서버 :** 결제 8건 + PG 파일 9줄 → 불일치 4유형(우리만·PG만·금액·상태)만 정확히 기록, 정상·자정 경계 건은 제외
    - **처리량 :** 대량 시드 데이터로 측정 예정 (처리 시간, 실패 후 재시작 시 절약 시간)
