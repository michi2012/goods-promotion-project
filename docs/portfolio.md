## 문제 해결·설계 결정

작업이 끝났을 때(PR 머지 후) 아래 **4개 질문이 모두 "예"**면 추가한다. 기능을 만든 것 자체가 아니라 **해결한 문제**를 적는다.

| 질문 | 거르는 것 |
|---|---|
| 1. **해결한 문제가 있었나?** 무엇이 잘못됐거나 위험했는지 영향(돈·데이터 정합성·장애·성능)을 한 문장으로 쓸 수 있다 | 단순 기능 구현 ("환불 API를 만들었다") |
| 2. **원인을 파고들었나?** 문제가 생기는 조건이나 근본 원인을 설명할 수 있다 | 원인이 뻔한 수정 (오타·설정 누락) |
| 3. **대안을 비교해서 골랐나?** | 정답이 하나뿐이던 수정 |
| 4. **해결을 증명할 수 있나?** 테스트·E2E·수치로 전후를 보여줄 수 있다 | 말로만 설명 가능한 것 |

- 같은 문제를 여러 PR로 풀었으면 **한 사례로 묶어** 마지막 PR 머지 후 적는다 (면접에서 몇 분 설명할 크기). 목록에 한 줄 + "사례"에 템플릿 형식.
- 리뷰 지적 반영·알람 조정처럼 그 문제의 일부를 고친 것은 따로 적지 않는다. 그 이야기를 풀 때 세부로 꺼낸다.
- 개발 프로세스·도구 개선(리뷰 skill 등)은 시스템 문제가 아니므로 이 표에 적지 않는다.

## 사례

### 작성 형식

```
### **[기술] 무엇을 해결했나 — 핵심 결정**

- **🚨 문제 : 한 줄 요약**
    - 상황과 영향(돈·정합성·장애·성능). 왜 기존 방식으로는 안 됐는지
- **⚖️ 대안 비교 및 기술 선정 :**
    - **선정 축 (대안 A vs <u>채택</u>) :** 검토한 이유와 고른 이유
    - **[대안 - 배제] :** 배제한 이유
    - **[방식 - 도입] :** 도입한 방식. 남는 한계와 보완 계획은 하위 항목으로
- **🛠️ 조치 : 한 줄 요약**
    - 실제로 적용한 설정·구조와 그 이유
- **📈 성과 : 한 줄 요약**
    - 테스트·E2E·수치로 본 전후
```

- 목록의 "원본"에 명세·PR을 링크하고, 사례에는 면접에서 말할 이유와 증거만 쓴다 (코드·설정 전체를 옮기지 않는다).

<a id="pg-reconciliation"></a>
### **[Spring Batch] 하루치 PG 대사의 정합성 확보 — 기존 스케줄러 대신 Spring Batch 도입**

- **🚨 문제 : 기존 스케줄러 방식으로 만들면 '틀린 감시선'이 되는 대사**
    - 실시간 보정(serverA 재대사 스케줄러)이 놓친 돈 흐름의 어긋남을 잡기 위해, **하루치 우리 결제 기록과 PG사 일자별 거래 파일을 비교하는 사후 대사**가 필요했습니다. 프로젝트의 기존 주기 작업(PG 취소 재시도 등)은 모두 `@Scheduled` + 조건부 UPDATE 선점 방식으로, **소량을 짧게 처리**하는 데 맞춰져 있었습니다.
    - 같은 방식으로 하루치 전체를 처리하면 정합성이 세 군데서 깨졌습니다 (각각 재현 테스트로 확인).
        - **중간 실패 시 전체 롤백 :** 한 트랜잭션으로 처리하면 N번째 건에서 DB 오류가 나는 순간 처리분이 모두 사라지고 처음부터 다시 해야 합니다.
        - **처리 중 대상 누락 :** 상태 조건 + OFFSET 페이징이면, 대사 도중 취소된 건만큼 페이지가 밀려 **대상 2건이 누락**됐습니다.
        - **실행 시점마다 다른 결과 :** '현재 상태'로 비교하면 D+1 새벽의 취소 전후로 D의 결과가 달라져 **오탐**이 생깁니다. 같은 날짜를 다시 돌리면 다른 결과가 나오는 감시선은 믿을 수 없습니다.
    - 운영 문제도 겹쳤습니다. 스케줄과 관리자 수동 실행이 **같은 날짜를 동시에** 돌릴 수 있고, 서버가 도중에 내려가면 **어디까지 처리했는지** 알 수 없습니다.

- **⚖️ 대안 비교 및 기술 선정 :**
    - **실행 프레임워크 (기존 `@Scheduled` + 직접 구현 vs <u>Spring Batch</u>) :** 새 의존성 없이 스케줄러 + JdbcTemplate + 진행 위치 테이블로 직접 만드는 방안을 먼저 검토했습니다. 하지만 chunk 단위 커밋, 진행 위치 저장, 실패 지점부터 재시작, 같은 날짜 중복 실행 방지를 **모두 직접 구현**해야 하고 그 코드 자체가 버그의 원천이 됩니다. 이를 JobRepository가 표준으로 제공하는 **Spring Batch를 채택**했습니다.
    - **[현재 상태로 비교 - 배제] :** 실행 시점에 따라 결과가 달라져 재실행 멱등성이 깨집니다.
    - **[이벤트 시각 컷오프 - 도입] :** 결제에 `approved_at`·`cancelled_at`을 기록하고, 대사일 D의 범위 [D 00:00, D+1 00:00) 안의 **승인·취소 이벤트만** 비교합니다. 컷오프 이후 변경은 다음 날 대사 대상이 되므로 언제 실행해도 결과가 같습니다.
    - **[OFFSET 페이징 - 배제] / [키셋 페이징 - 도입] :** `(이벤트 시각, id)`를 정렬 키로 쓰는 키셋 페이징을 적용했습니다. 조회 조건이 이벤트 시각뿐이라 처리 중 상태가 바뀌어도 대상이 흔들리지 않고, 마지막 키가 Step 실행 컨텍스트에 저장돼 **그대로 재시작 위치**가 됩니다.
    - **[INSERT IGNORE - 배제] / [ON DUPLICATE KEY UPDATE - 도입] :** chunk 재시도·재시작으로 같은 행을 다시 써도 결과가 한 벌만 남아야 합니다. IGNORE는 길이 초과·형 변환 오류까지 경고로 삼켜 대사 대상이 **조용히 빠지는** 문제가 PR 리뷰에서 드러나, 유니크 충돌만 무시하고 나머지 오류는 Step 실패로 드러나게 바꿨습니다.
    - **[불일치 자동 보정 - 배제] :** 잘못 보정하면 돈이 움직입니다. **기록 + P1 알람**만 하고 처리는 사람이 합니다.
    - **[날짜 경계 5분 허용 - 도입] :** 우리와 PG의 기록 시각 차이로 자정 전후 건이 오탐으로 잡힙니다. 한쪽에만 있는 후보는 상대편에서 5분 이내의 같은 이벤트를 찾아 제외합니다. "PG 시각 ≤ 우리 기록 시각"이라는 불변식 덕분에 다음 날 파일 없이 **전날 파일의 마지막 5분만** 읽으면 됩니다.
        - **남은 한계 :** 거래 파일이 서버 로컬 디렉터리라 **단일 인스턴스 전제**입니다. 다중 파드는 공유 저장소(EFS·S3) 결정 후 보완할 예정입니다 (BL-048).

- **🛠️ 조치 : 정합성을 지키는 Job 설정과 운영 연결**
    - **Job 구성 (7 Step, chunk 500 커밋) :** 이전 결과 삭제(재실행 시 교체) → 전날 파일 꼬리 적재 → 당일 파일 적재(**없으면 FAILED**) → 우리 승인→PG → 우리 취소→PG → PG→우리 → 요약. 승인·취소는 정렬 키가 달라 Step을 나눴습니다.
    - **설정마다 이유가 있습니다 :** 기동 시 Job 자동 실행 금지(`spring.batch.job.enabled: false`), 메타 테이블은 Flyway로 관리(`initialize-schema: never`), Reader는 Step 범위로 만들어 실행마다 대사일을 주입, 당일 파일은 없으면 실패·전날 파일은 없어도 진행.
    - **실행 진입점 :** 매일 03:00 스케줄과 관리자 API를 두고, 그 날짜의 마지막 실행을 보고 결정합니다. **FAILED면 같은 파라미터로 실행 → Spring Batch 재시작**, COMPLETED면 `requestedAt` 파라미터를 더해 새 JobInstance로 실행(결과 교체), 실행 중이면 409. 실행은 비동기라 다른 작업과 공유하는 스케줄러 스레드를 붙잡지 않습니다.
    - **서버 재기동 대응 :** 서버가 대사 도중 내려가면 실행이 STARTED로 남아 **재시작도 새 실행도 막힙니다** (Spring Batch가 자동으로 정리해 주지 않음). 기동 시 이런 실행을 FAILED로 정리해 다음 실행이 실패 지점부터 이어지게 했습니다.
    - **메트릭·알람 :** 메트릭은 Step이 아니라 **Job 종료 리스너**에서 갱신합니다 (Step 재시도 시 중복 집계 방지). 불일치·Job 실패·30시간 미실행을 P1 알람으로 두고, 미실행 기준 시각은 **대사일의 끝(D+1 00:00)**으로 잡았습니다. 대사일 시작으로 잡으면 정상 운영에서도 매일 알람이 울립니다.

- **📈 성과 : 재현 테스트로 증명한 정합성과 실제 서버 판정**
    - **재현 테스트 3종 — 단순 구현은 실패, Job은 통과 :**
        - 재시작 : 한 트랜잭션은 전체 롤백 / Job은 커밋분을 유지하고 완료 Step을 건너뛴 채 **남은 4건만 읽어 최종 6건** — 한 번에 성공한 결과와 동일
        - 키셋 : OFFSET은 처리 중 취소로 **2건 누락** / 키셋은 **6건 모두 판정**
        - 컷오프 : 현재 상태 비교는 다음 날 취소 전후로 결과가 바뀜 / Job은 재실행해도 동일하고 결과는 한 벌로 교체
    - **실제 서버 확인 :** 우리 결제 8건 + PG 파일 9줄 → **불일치 4유형(우리만·PG만·금액·상태) 각 1건만** 기록, 정상 4건과 자정 경계 1건은 제외. 같은 날짜 재실행 시 4건 유지.
    - **장애 복구 E2E :** PG 파일 없음 → Job FAILED·실패 메트릭 +1 → 재실행 시 RESTART, **완료된 Step은 다시 돌지 않음**.
