# PG 대사 배치 — 건별 조회 → chunk 일괄 조회 전후 비교 — 2026-11-17

BL-008. 기준선 `docs/perf/2026-11-17-pg-reconciliation-baseline.md`.

- 가설: 비교 Step(우리→PG, PG→우리)이 건마다 상대편을 1회 조회해(100만 기준 약 210만 쿼리) 전체의 약 75%를 쓴다. chunk 단위 `IN` 조회 1회로 바꾸면 비교 Step이 크게 줄고 판정 결과는 같다.
- 바꾼 것 (하나): 비교 Step 3개의 조회 방식. `ItemProcessor`의 건별 조회 → `ItemWriter`가 chunk(500)의 주문 ID로 `IN` 조회 1회 후 기존 `ReconciliationMatcher`로 판정·저장 (조회·판정·저장이 같은 chunk 트랜잭션). chunk 크기·그 외 설정 동일
- 환경: 기준선과 같음 — 로컬 docker compose 한 대, serverC CPU 1.0·메모리 2G, 다른 부하 없음. **절대 수치는 운영 근거가 아님**
- 데이터: 같은 시드(`perf/seed/pg-reconciliation-seed.mjs` seed 47, 결정적 — 같은 파일 재사용), 대사일 2026-10-04, 결제 100만 / 우리 이벤트 1,047,540 / PG 줄 1,049,009
  - 조건 차이: 개선 전 측정 때는 다른 날짜 시드(10만·1만, 약 11만 행)가 테이블에 함께 있었고 개선 후에는 없었다 (100만 대비 약 10%, 대상 날짜 조회는 날짜 인덱스로 거른다)
- 실행: 관리자 API, 같은 날짜 재실행 3회 (모두 이전 결과 교체 = 재실행 조건). 개선 전은 같은 날 측정한 기준선 재실행 값 재사용
- 반복: 3회 중앙값(최소~최대)
- **정확성**: 개선 후 모든 실행에서 유형별 불일치 993/988/1,004/982 = 기대값. 판정 테스트(재현 3종·Job·Matcher·Metrics) 통과

- 판단: **개선.** 차이가 반복 간 편차(약 5%)보다 훨씬 크고, 줄어든 시간이 바뀐 Step에만 나타나며 바꾸지 않은 Step(clear·loadDay)은 그대로라 원인이 조회 방식임을 설명할 수 있다.
- 병목 이동: 개선 후에는 clear(약 54초) + loadDay(약 108초)가 전체의 절반 이상. 재실행일 때만 있는 대량 DELETE와 그 직후 적재 지연이 주원인 → BL-054(조건부, 매일 03:00 첫 실행에는 해당 없음).
- 실시간 간섭: 비교 Step은 `payments`를 일반 SELECT(잠금 없는 일관된 읽기)로만 읽고, 쓰기는 대사 테이블에만 한다 — 측정하지 않음.
