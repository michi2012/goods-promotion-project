# PG 대사 배치 기준선 — 2026-11-17

BL-047 (BL-002 PR③). 명세 `docs/specs/pg-reconciliation-batch.md`. 개선 전후 비교가 아니라 **현재 구현의 기준선**과, 처음부터 적용한 설정(일괄 쓰기)·chunk 크기의 효과 확인이다.

- 가설: ① 하루 10만 건(현실 상한)·100만 건(10배 여유) 모두 03:00 실행 창(업무 시작 전 수 시간) 안에 넉넉히 끝난다 ② 처리 시간은 규모에 비례한다 ③ 실패 후 재시작은 남은 분량만 처리해 전체 재실행보다 짧다 ④ 일괄 쓰기를 끄면 PG 줄 적재가 느려진다 ⑤ chunk 크기는 커밋 횟수만큼 시간에 영향을 준다
- 환경: 로컬 docker compose 한 대(Windows). serverC CPU 1.0·메모리 2G 제한, mysql-c 전용 컨테이너. 다른 부하 없음. **절대 수치는 운영 근거가 아니라 이 환경의 기준선**
- 설정(기준): chunk 500, `rewriteBatchedStatements=true`, 경계 허용 5분
- 데이터: `perf/seed/pg-reconciliation-seed.mjs` seed 47. 정상 승인 약 94.5%, 승인+취소 5%, 자정 경계 0.05%, 불일치 4유형 각 0.1%
  | 규모 | 대사일 | 결제 | 우리 이벤트(D) | PG 줄 | 기대 불일치 (우리만/PG만/금액/상태) |
  |---|---|---|---|---|---|
  | 1만(검증) | 2026-10-01 | 10,000 | 10,486 | 10,497 | 5 / 7 / 5 / 7 |
  | 10만 | 2026-10-02 | 100,000 | 104,800 | 104,945 | 90 / 106 / 92 / 86 |
  | 100만 | 2026-10-04 | 1,000,000 | 1,047,540 | 1,049,009 | 993 / 988 / 1,004 / 982 |
  - 10만은 D-1(2026-10-01) 파일이 있어 꼬리 46줄 적재, 100만은 D-1 파일 없음 (차이 0.5초 이하)
- 실행: 관리자 API `POST /api/v1/payments/admin/reconciliations?date=` (03:00 스케줄과 같은 Job). 같은 날짜 재실행 = 새 실행(Step 1이 이전 결과 삭제)
- 지표: `BATCH_JOB_EXECUTION`·`BATCH_STEP_EXECUTION`의 시작·종료 시각, READ/WRITE/FILTER/COMMIT 건수. 처리량 = (우리 이벤트 + PG 줄) / Job 소요 시간
- 반복: 설정마다 워밍업 1회 + 3회 (100만은 10만 측정 직후라 워밍업 생략). 수치는 3회 중앙값(최소~최대)
- **정확성**: 모든 측정 실행에서 유형별 불일치 건수가 기대값과 정확히 일치

## 3. 설정 비교 (10만, 같은 날 측정)

한 번에 하나만 바꿨다. 기준은 1절의 10만 재실행 값.

|---|---|---|---|
| **기준** chunk 500, 일괄 쓰기 켬 | 59.5초 (57.4~60.5) | — | |
| 일괄 쓰기 끔 (`rewriteBatchedStatements=false`) | 72.9초 (71.4~74.0) | **+23%** | loadDay 6.6 → 23.1초(3.5배). 쓰기가 많은 Step만 느려지고 비교 Step(쓰기 수백 건)은 그대로 |

- 기준 반복 간 편차(약 5%)보다 모든 차이가 크다.

- chunk 2000은 설정만으로 18% 단축. 단 chunk가 크면 실패 시 다시 처리하는 분량과 한 트랜잭션의 잠금 범위가 커진다 — BL-008에서 실시간 간섭과 함께 판단.

## 4. 판단 — BL-008

- **운영상 급하지 않음**: 100만(10배 여유)도 약 12분. 실행 창 대비 충분.
- **개선 후보는 측정으로 확인됨** (영향 큰 순):
  1. 건별 조회(N+1) — 비교 Step 두 개가 전체의 약 75%. 건마다 조회 1회(100만 기준 약 200만 쿼리) → chunk 단위 일괄 조회
  2. chunk 크기 — 2000에서 −18% (설정만). 1번 뒤 다시 측정
  3. 재실행 시 대량 DELETE — 100만에서 약 95초 추가. 나눠서 삭제 또는 날짜별 파티션
- 멀티스레드·파티셔닝: 로컬 serverC가 CPU 1개라 의미 있는 비교가 안 돼 측정하지 않음.
- 다음 순서(사용자 합의): 레거시 구현(한 트랜잭션·OFFSET·건별) vs Batch 비교(새 항목) → BL-008.

## 5. 측정 중 발견

- **D-1 파일이 늦게 들어온 뒤 재시작하면 경계 건이 오탐**: D-1 파일이 없는 상태로 loadPrevTail이 0줄로 COMPLETED되면, 이후 D-1 파일이 생겨도 재시작은 그 Step을 다시 돌지 않는다 → 자정 경계 건이 "우리만 있음"으로 기록됨 (워밍업 실행 29에서 2건 재현). 오탐만 생기고 돈은 움직이지 않음 → 백로그.
